# Component `secrets/vault-server`

The official [HashiCorp Vault](https://developer.hashicorp.com/vault) server
(Helm `hashicorp/vault`, chart `0.34.1`, appVersion `2.0.4`) as a **self-managed
Vault instance** running in **standalone** mode with file storage on a persistent
volume.

This component is a **second implementation** of the `vault-secrets` capability,
complementary to [`secrets/vault-operator`](../vault-operator/) (bank-vaults). The
two differ in the unseal model, which is the reason both exist:

- **`vault-operator`** auto-initializes and **auto-unseals**, storing the unseal
  keys in a backend (a Kubernetes Secret or a cloud KMS). Operationally
  self-healing, but the keys are machine-readable in-cluster.
- **`vault-server`** (this component) comes up **sealed** and is unsealed **by
  hand** (`vault operator init` + `vault operator unseal`). The key shares are held
  under **human custody** and are never machine-readable in-cluster — the model a
  human-custody security root requires. bank-vaults cannot do this.

`kind: mixed`: the chart renders the StatefulSet, Services, RBAC, ConfigMap, and
ServiceAccount; `manifests/00-namespace.yaml` ships the dedicated Namespace (the
chart has no Namespace template). The chart ships **no** CustomResourceDefinitions,
so there is no strict-B `-crds` split.

## Contents

- `helm/vault-server.yaml` — Vault chart reference (`0.34.1`) + default values:
  standalone plaintext baseline, PVC-backed storage, injector off, the
  `system:auth-delegator` ClusterRoleBinding suppressed, and the explicit
  securityContext pins for PSA `restricted`.
- `manifests/00-namespace.yaml` — the dedicated `vault-server` Namespace with the
  PSA `enforce: restricted` label (sole-claimant rule, ADR-0027).

## Namespace & Pod Security

The server occupies the **dedicated** `vault-server` namespace (`enforce:
restricted`). The StatefulSet is provably `restricted`-compliant: pod
`runAsNonRoot: true` + `runAsUser: 100` + `runAsGroup: 1000` + `fsGroup: 1000` +
`seccompProfile: RuntimeDefault`, and the vault container
`allowPrivilegeEscalation: false` + `capabilities.drop: [ALL]`. The chart dropped
`IPC_LOCK` (swap is expected to be disabled on nodes), so `disable_mlock = true` is
auto-injected — see the swap note under **Consumer obligations**. Per ADR-0027 the
**consumer** adds the `pod-security.kubernetes.io/enforce-version` pin (its cluster
minor) and any PNI labels in its Argo overlay.

## Operational model — sealed until manually unsealed

The readiness probe is an exec of `vault status -tls-skip-verify` (exit `2` while
sealed → Not Ready). Consequently:

- **On first install** the pod is Not Ready until an operator runs `vault operator
  init` (generating the key shares + root token) followed by `vault operator
  unseal` (3 of 5 shares by default). The Argo Application sits
  **Progressing/Degraded** during this window — this is the **expected operational
  signal, not a fault**.
- **After every pod restart** (crash, node drain, upgrade) the pod returns sealed
  and Not Ready and MUST be **manually re-unsealed**. A sealed Vault serves no
  secrets.
- `updateStrategyType: OnDelete` — Vault pods are **not** replaced during a Helm
  upgrade until manually deleted. This is intentional, giving the operator explicit
  control over the seal/unseal cycle per upgrade.

## Consumer obligations (Layer 3)

These are MUSTs the consumer cluster repo owns — the catalog baseline does not
model them.

- **A default StorageClass MUST exist**, or the consumer MUST overlay
  `server.dataStorage.storageClass` via a StatefulSet Kustomize patch. Without a
  matching StorageClass the StatefulSet's PVC stays `Pending` and the pod never
  starts. `compatibility.yaml requires: {}` is intentional — this is a cluster
  precondition, not a catalog-internal dependency (any block-storage implementation
  satisfies it).
- **Unseal key shares + root token MUST NOT be stored in-cluster, in a Kubernetes
  Secret, or committed to git.** They are generated by `vault operator init` at
  first deploy and distributed **offline** to key custodians under human custody.
  Loss of a threshold number of shares requires re-initialization and invalidates
  all stored secrets.
- **TLS is a production MUST — see §TLS.** The baseline listener is plaintext.
- **An audit device MUST be configured before production use.** The baseline ships
  **no** audit device (`auditStorage.enabled: false`; the default HCL has no
  `audit` stanza), so Vault records nothing — not unseal operations, not root-token
  use, not any secret read. Enable at least one, e.g. `vault audit enable file
  file_path=/vault/audit/vault_audit.log`.
- **Verify swap is disabled on the nodes running Vault.** `disable_mlock = true` is
  auto-injected (the chart dropped `IPC_LOCK`), which lets the kernel page Vault
  process memory — including unsealed key material — to swap. Disabling swap on the
  nodes is the mitigation.

## TLS

The baseline renders with `global.tlsDisable: true` (chart default), so the Vault
API listener is **plaintext HTTP for the deployment's whole lifetime** — every
client token and secret read traverses the pod network **unencrypted** on every
request (including from in-cluster consumers such as `secrets/external-secrets` and
`secrets/vault-config-operator`).

**Enabling TLS requires re-rendering with `global.tlsDisable: false` — a consumer
Kustomize patch CANNOT do it.** The `vault.scheme` helper derives the scheme from
that render-time flag and hard-codes `VAULT_ADDR`, `VAULT_API_ADDR`, the container
port names, and the readiness-probe scheme into the signed StatefulSet. Patching
only the ConfigMap HCL to remove `tls_disable = 1` yields a pod that speaks
plaintext HTTP at a TLS listener → the readiness probe fails permanently → the pod
never becomes Ready.

Until a TLS delivery path is chosen (a TLS-rendered variant, a consumer re-render
workflow, or deferral — undecided, see #827), the **baseline in-cluster protection
is a consumer-authored NetworkPolicy** restricting reach to the Vault listener.
This is a **production MUST** before exposing Vault to in-cluster consumers.

## Capability

Provides `vault-secrets` (id `vault-secrets`, `swap_class: data-migration`) — an
in-cluster Vault instance exposing the KV secret-access API. This is a **second
active implementation** of that capability alongside `secrets/vault-operator`
(different upstream chart, direct-StatefulSet vs. CR-reconciled model); the two are
**not** topology variants and **not** mutually exclusive (a cluster may run both).
Swapping implementations means migrating the stored secret data (`data-migration`).
The chart exposes no CRD/API surface (`api_surface: []`).

## Out of scope

- **A TLS listener** (render-time `global.tlsDisable: false`; not a Kustomize
  overlay — see §TLS).
- **Non-Shamir seal** (transit auto-unseal / cloud KMS) — render-time
  `server.seal.*` values, a consumer concern.
- **HA Raft-integrated-storage topology** — the catalog default is standalone
  single-replica.
- **An audit device** — the baseline ships none; the consumer configures one before
  production (see Consumer obligations).
- **The Kubernetes auth method** — requires the `system:auth-delegator`
  ClusterRoleBinding, suppressed here (`server.authDelegator.enabled: false`); a
  consumer ships it as a supplemental manifest if needed.
- **The Vault Agent Injector and CSI provider** — disabled; shipped separately if a
  consumer needs them.
- **Break-glass unseal recovery runbook** — operational content in
  talos-platform-docs.
